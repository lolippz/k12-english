K12 英语单机学习应用 · 实施方案

版本 v0.2（取代 v0.1 的服务端方案） 日期 2026-10-13 形态 学生端单机应用

范围收窄后，结论变化

「自用、不对外、只要学生端」这个约束，把项目的复杂度砍掉了约 70%，同时把三条最重的风险直接清零。

  1. 合规风险归零：教育 App 备案、双减、未成年人个人信息保护，全部只约束"向公众提供服务"的运营方。自用不适用。
  2. 服务端归零：没有账号、没有多租户、没有并发，所有数据存本机，零服务器成本、零运维。
  3. GPL 风险归零：qwerty-learner（GPL-3.0）的代码从"只能参考"变成"可以直接抄"。不分发就不触发任何义务；即便拷给学生，提供源码即可。
  4. 剩下的唯一硬工作量是数据准备——把散落在几个开源项目里的词库、释义、语料、音频，整理成一个可离线内联的数据包。

二、单机架构

三层，全部运行在本机，无任何网络依赖（除可选的 AI 批改）。

层次组成说明
界面层 今日任务 · 背单词 · 听力跟读 · 阅读 · 练习 · 学情统计 单页应用，路由切换，无登录
引擎层 FSRS 调度 · 发音朗读 · 录音与识别比对 · 本地批改 全部跑在前端，无需服务端进程
数据层 词库模块 · 例句短文 · 听力音频 · 学习记录 前三项随程序打包；学习记录存本地存储

一个关键工程细节：数据不要用 fetch 读本地 JSON 文件。直接用 file:// 打开页面时，浏览器会以 CORS 策略拦截本地文件请求。正确做法是把词库编译成 JS/TS 模块（构建时内联），用 import 引入——既绕开 CORS，也避免额外的文件读取层。

三、交付形态：三条路线

路线形态优点缺点
A · 本机 Web 应用
推荐起步		 Vite 构建，双击一个 start.bat 起本地服务并打开浏览器 开发最快，改一行立刻见效；调试方便；零打包成本 需要机器上有 Node 或 Python 运行时
B · Tauri 桌面应用
推荐交付		 复用 A 的全部前端代码，Tauri 套壳打包成免安装 exe 双击即用，无需任何环境；体积约 10 MB；可存本地 SQLite；内嵌 WebView2（Edge 内核） 首次需要装 Rust 工具链编译一次
C · Electron 同样套壳，打包成 exe 上手最简单，生态最熟 体积 150 MB 起，对一个学习工具过重

建议路径：A → B。先用路线 A 把内容和交互跑通（前端代码 100% 可复用），确定好用之后再套 Tauri 打成 exe。两条路线的前端代码完全一致，切换成本接近于零。

四、自用场景的"零成本能力"清单

这是范围收窄后最大的红利——原来需要采购或自研的能力，现在都能用本机已有的东西替代。

需求零成本方案说明
单词 / 例句发音edge-tts 预生成 mp3微软在线语音，音质接近真人，批量生成后随应用打包，完全离线可用。比浏览器内置 TTS 好听得多。
跟读评测MediaRecorder 录音 + 回放对照最低成本版本：录音 → 回放 → 自己对照原文。自用完全够。
跟读自动比对
（进阶）		whisper.cpp 本地识别 → 与标准文本做词级比对能指出"哪个词读错了"。模型文件 tiny 约 75 MB / base 约 150 MB，可离线。或直接调云端 ASR API。
记忆调度ts-fsrs（MIT）纯 TypeScript，浏览器直接跑，无需后端。
语法批改LLM API（DeepSeek / 通义等）自用直接调 API 最省事，一篇作文成本约几分钱。LanguageTool 自托管需要 Java，本地部署反而更重。
文本难度分级textstatFlesch-Kincaid 公式自动估算阅读难度，用于阅读材料排序。
数据存储IndexedDB（路线 A）/ SQLite（路线 B）本地持久化，另做 JSON 导出导入用于备份与换机。

需要留意的一点：浏览器的 SpeechRecognition 接口在 Chrome / Edge 中依赖在线服务，在 Tauri 的内嵌 WebView2 里不保证可用。所以跟读评测建议按上表分两层做：先做"录音 + 回放对照"（零依赖、必然可用），需要自动比对时再接 whisper.cpp 或云端 ASR。不要把它设计成强依赖。

五、功能清单（学生端全量）

P0 · 核心闭环（先做这些）

P0

今日任务

FSRS 算出的今日待复习词 + 新词配额，一个按钮进入。这是唯一的入口，学生不需要做任何选择。

P0

背单词三模式

拼写（听音打字）、听音选义、看义选词。每张卡带音标、释义、例句、发音。答完立即反馈并写回 FSRS 状态。

P0

学情统计

连续打卡天数、累计掌握词数、每日学习量曲线、正确率趋势。自用场景下这是坚持下去的主要动力。

P0

错题本

反复答错的词自动归集，可单独重练。数据直接来自答题记录，无需额外录入。

P1 · 能力扩展

P1

听力跟读

播放音频 → 录音 → 回放 → 原文对照。进阶版接入识别比对。

P1

分级阅读

精选短文（StoryWeaver CC-BY 绘本 + 公版短篇），点任意词即时查义、一键加入词表。

P1

词汇与语法练习

选择题与填空题，题目从词库自动生成（选词填空、词形变化），无需人工出题。

P1

数据导出 / 导入

学习记录导出为 JSON，用于备份与换机迁移。单机应用必备。

P2 · 可选增强

P2

写作批改

提交短文，调 LLM 返回错误标注、评分与改进建议。需要配置一个 API Key。

P2

口语对话

与 AI 自由对话（语音识别 + LLM + TTS）。成本与复杂度最高，最后做。

六、数据准备：唯一的重活

这一步决定产品能不能用。四类数据源，加工成四个内联模块。

数据源取什么怎么处理产出
qwerty-learner 中考词库、高考词库（JSON） 直接拉取，按学段合并去重 约 3500-5000 词的词表骨架
ECDICT 释义、音标、BNC/COCA 词频、考试标签 用上一步的词表做 join，只保留命中词条，丢弃其余 75 万条 词库主数据，约 2 MB
StoryWeaver / Gutenberg CC-BY 分级绘本、公版短篇 按 textstat 难度排序，选 100-200 篇入库 分级阅读语料
edge-tts — 对词表 + 例句批量合成 mp3（约 5000 词 + 例句，可分批） 听力与发音音频，约 20-40 MB

体积估算：词库 2 MB + 语料 3 MB + 音频 30 MB ≈ 35-45 MB。这对一个桌面应用完全合理，且全部离线可用。如果嫌音频大，可以只对核心 1500 词生成音频，其余用浏览器 TTS 兜底。

七、实施步骤

Step 1 · 数据准备1 天

写一个 Python 脚本：拉 qwerty-learner 词库 → 与 ECDICT CSV 做 join → 输出 words.ts（约 5000 词）。这一步做完，产品的内容底座就定了。

Step 2 · 项目骨架半天

Vite + React + TypeScript + Tailwind 初始化；接入 ts-fsrs，先写一个纯逻辑脚本验证调度行为符合预期。

Step 3 · 核心闭环2-3 天

今日任务 → 背单词三模式 → 答题记录写回 → FSRS 更新下次复习时间 → 学情统计。数据用 IndexedDB 持久化。这一步跑通，产品就已经可用了。

Step 4 · 听力与跟读1-2 天

edge-tts 批量生成音频；实现播放、录音、回放、原文对照。

Step 5 · 阅读与练习2-3 天

分级阅读页（点词查义、加入词表）；词汇与语法练习自动出题。

Step 6 · 打包交付半天

按需套 Tauri，打包成免安装 exe。

合计约 10-14 个工作日（业余时间约 3-4 周）可得到一个完整可用的单机版本。相比 v0.1 的 SaaS 方案，周期缩短了一半以上。

八、剩余风险

数据加工脚本的工作量ECDICT 与词表的 join、字段清洗、例句筛选是纯体力活，且容易在音标编码、多义项排序上出细节问题。缓解：先只做"词 + 释义 + 音标 + 发音"四个字段跑通闭环，例句和词频后补。
语音识别在 WebView2 中不可用不要把它设计成强依赖。跟读评测的基线版本用"录音 + 回放对照"，自动比对作为可选增强。
内容量不足以支撑长期使用5000 词对初中三年是够的，但高中可能需要 8000+。缓解：词库设计成可扩展的数据模块，后续追加词表只需改数据不改代码。
坚持不下去这是单机自用项目最大的真实风险——没有外部监督。缓解：P0 阶段就把"连续打卡"和"每日任务"做扎实，用可见的进度曲线维持动力。
